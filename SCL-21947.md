## 2. The mental model (read this first)

scalac canonicalises path-dependent types through a few well-factored operations on
`Type`: `asSeenFrom`, `baseType`/`baseTypeSeq`, `memberType`, and prefix-following in
`TypeComparers`. **`memberType` is the keystone**: a member's type is resolved to its
**most-specific override** and then `asSeenFrom`'d onto the access path.

IntelliJ, pre-branch, pointed designators/projections at the **declaration-site**
element. So when the cake pattern overrides an abstract member further down a prefix's
linearization — e.g.

```scala
class Global { val gen: TreeGen { val global: Global.this.type } = ... }   // refinement override
// or
trait NscGen { val global: SymbolTable }; object gen extends NscGen { ... } // object override
```

…IntelliJ resolved `pre.gen.global` through the *abstract* `global: SymbolTable`, not the
override `global: Global.this.type`. The singleton path never collapsed, `asSeenFrom`
had the wrong prefix to rewrite, and conformance bottomed out comparing unrelated
`this`-types → **false mismatch**.

The fix, restated once: **make IntelliJ's member-type resolution override-aware
(`pre.memberType`), and make its prefix-following collapse singleton val-paths** — then
the four scalac primitives fall into line. Because IntelliJ re-derives these facts in
*several* subsystems (substitution, projection types, conformance, resolution,
equivalence), the same invariant had to be restored in each place independently.

**The cake `this`-instance equality** (`trait Types { self: SymbolTable => }`,
`class SymbolTable extends Types` — `Types.this` and `SymbolTable.this` are the same
instance) is the secondary theme. scalac canonicalises these to one symbol; IntelliJ
does not, so `ScThisType.sameThisInstance` was added to equate them. **This is the main
open soundness question** (§7).

## 4. How to run the tests (this saved a multi-hour detour — READ IT)

From the repo root, **use the ROOT project's `testOnly`, NOT `scala-impl/testOnly`.**
`scala-impl/testOnly` runs a config lacking the bundled Maven plugin, so every test dies
in `setUp` with `Missing extension point: com.intellij.repositoryLibrary` (a.k.a.
`LibraryKind:Scala is not registered`). That error is **not** stale jars or SDK drift —
do not chase clean builds for it.

```bash
# whole suite
sbt "testOnly org.jetbrains.plugins.scala.annotator.OverrideHighlightingTest"

# single method (junit-interface syntax, NOT ScalaTest -t)
sbt "testOnly ...OverrideHighlightingTest -- --tests=testSCL21947TreeGen"

# after editing main sources — incremental packaging is enough, even for NEW classes:
sbt packageArtifact "testOnly ...OverrideHighlightingTest"

# the TCK
sbt packageArtifact "testOnly ...typeSystemTck.TypeSystemTckTest"
```

- **The plugin the tests load is `./target/plugin/Scala/lib/*.jar` (ROOT project)**, not
  `scala/scala-impl/target/plugin`. Verify what's actually packaged with
  `unzip -l ./target/plugin/Scala/lib/scalaCommunity.jar | grep <Class>`.
- **Debug tracing:** gate on a system property (e.g. `System.getProperty("scala.tck.trace")`),
  set it via `System.setProperty` in the test body, print to `System.err`. Trace the
  *conformance/resolution* path, not the type printer — several of these bugs render a
  correct-looking type while resolving/comparing the wrong one.
- If you're in a **git worktree**, confirm you're running in the worktree, not the main
  checkout.

## 7. Open soundness questions

1. **`sameThisInstance` over-equates the literal cake `this`-pair.** With
   `trait Types { self: SymbolTable => }` + `class SymbolTable extends Types`, PSI returns
   `SymbolTable.this.T =:= Types.this.T` **true**, but scalac says **false** (it
   canonicalises only *within one instance* via asSeenFrom/override matching, not the
   literal forms). Correct where override-matching needs it (`testSCL21947Cake`), but
   observably more lenient than scalac for a raw `=:=`/`<:<`. Cannot be a green TCK
   corpus entry (conformance/equivalence are deferral-free hard assertions) — recorded as
   a "Known divergence" in the TCK README. **This is the headline risk to review.**
   Question for Jason/next agent: can `sameThisInstance` be gated to fire only in the
   override-matching context, not general `=:=`?
2. **Trait self-type recursion guard.** `ThisTypeSubstitution.hasRecursiveThisType` now
   carves out objects (terminal) but still resolves the *trait* self-type case coarsely
   with `isSameOrInheritor`. The SCL-18532 ↔ SCL-3654 tension is untouched
   (SCL-18532's original perf fix disabled `testSCL3654`). A principled fix would be
   direction-aware. **Needs a perf re-confirmation opening scala/scala `Typers.scala`**
   before any change here (the original bug was 600% CPU / `recursiveUpdate` blowup).

## 8. Remnant gaps / follow-up work (concrete next steps)

1. **`packedType` covers only singletons.** `ScBlock.avoidLocalSingletons` widens
   block-local *singletons* but not block-local **classes/objects**, which scalac
   existentially abstracts. A block whose last expression has a local-class type still
   leaks it. Largest correctness gap; needs a local-symbol-escape check + widening.
2. **`baseTypeSeq` ordering + `ScThisType` linearization.** Ordering is by
   `(-baseClassCount, qualifiedName)`, not scalac's symbol-id tie-break. TCK linearization
   is green everywhere *except* the `ScThisType` self-type case `04 AnimalBoxThis` — the
   residual `BaseTypes` self-type ordering issue (latent under resolution/conformance,
   which have their own selfType fallbacks).
3. **Consolidate the three `memberType` code paths.** The effect is currently restored
   in resolution (`BaseProcessor`), conformance (`ScalaConformance` collapse), and
   equivalence (`ScProjectionType.equivInner`), hand-synced. Intended end-state: the
   override-aware `designatorSingletonType` subsumes the conformance-side helpers (blocked
   today only by the compound-refinement case, §6). Do the cleanup guided by the
   sensitivity map.
4. **Perf.** `overrideSingletonOf` calls `TypeDefinitionMembers.getSignatures(cls).forName`
   on the hot projection conformance/equivalence path. Flagged, not yet profiled.
5. **PR #5 review items** — the `sameThisInstance` soundness note (§7.1) is the open PR
   discussion point.
